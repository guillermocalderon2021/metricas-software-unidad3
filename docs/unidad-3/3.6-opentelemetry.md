# 3.6 OpenTelemetry: instrumentación, contexto y exportación de trazas

## Propósito

En las sesiones anteriores, `orders-api` se utilizó para estudiar métricas de servicio, PromQL, dashboards y alertas. Ese trabajo permitió observar comportamiento agregado: tasa de solicitudes, proporción de errores, solicitudes en ejecución y distribuciones de duración.

La rama `3.6-opentelemetry` introduce un segundo servicio:

```text
cliente
   |
   | POST /orders
   v
orders-api
   |
   | POST /authorize
   v
payment-api
```

Los escenarios `normal`, `slow` y `payment-timeout` se mantienen, pero la autorización de pago ocurre ahora mediante una llamada HTTP real entre dos procesos.

Esta modificación introduce una nueva pregunta operacional:

> Para una solicitud de creación de orden, ¿qué operaciones se ejecutaron en cada servicio, cómo se relacionan y cuánto tiempo consumió cada una?

OpenTelemetry proporciona el modelo de instrumentación y el contexto necesarios para producir esa evidencia.

Al finalizar la sesión se deberá poder:

1. describir una traza mediante spans, relaciones padre-hijo e identificadores de contexto;
2. explicar cómo el contexto se conserva dentro de un proceso y se propaga entre `orders-api` y `payment-api`;
3. distinguir qué información puede obtenerse mediante instrumentación automática y qué requiere instrumentación manual;
4. explicar el recorrido de una traza desde la aplicación hasta un backend mediante OTLP y OpenTelemetry Collector.

---

## 1. El caso de estudio: `orders-api` y `payment-api`

La creación de una orden comienza en:

```text
POST /orders
```

`orders-api` valida el escenario y solicita una autorización a:

```text
POST /authorize
```

en `payment-api`.

Los comportamientos continúan siendo deterministas:

| Escenario | `payment-api` | Resultado de `orders-api` |
|---|---:|---|
| `normal` | responde en aproximadamente 80 ms | HTTP 201 |
| `slow` | responde en aproximadamente 350 ms | HTTP 201 |
| `payment-timeout` | responde en aproximadamente 700 ms con HTTP 504 | HTTP 504 |

Las métricas ya utilizadas permiten observar estos cambios sobre muchas solicitudes. Por ejemplo, el histograma:

```text
orders_http_request_duration_seconds
```

permite obtener media, p95 y distribución aproximada de duración.

Una serie temporal puede mostrar que el p95 aumentó. No representa, por sí misma, la estructura interna de una solicitud particular.

Para una solicitud concreta se necesita una representación como:

```text
POST /orders                            357 ms
|
+-- order.create                        355 ms
    |
    +-- POST /authorize                 352 ms
            |
            v
        payment-api
        POST /authorize                 350 ms
        |
        +-- payment.authorize           349 ms
```

Esta estructura permite observar:

```text
qué operaciones participaron
qué operación llamó a cuál
qué servicio ejecutó cada operación
cuándo comenzó y terminó cada una
dónde se observa la mayor parte del tiempo
```

Una **traza** representa este tipo de ejecución.

![Métricas, logs y trazas sobre una misma solicitud](images/3.6-metricas-logs-trazas.png)

### 1.1 Lo que una traza puede establecer

Considérese:

```text
POST /orders                            706 ms
|
+-- POST /authorize                     701 ms
        |
        +-- payment.authorize           700 ms
```

La evidencia permite afirmar que la mayor parte de la duración de `POST /orders` se observa dentro del camino de autorización de pago.

No permite afirmar todavía que la causa sea:

```text
CPU
red
I/O
contención
saturación
bloqueo
```

La traza localiza dónde se observa el tiempo. La explicación del mecanismo puede requerir otras fuentes de evidencia.

## 2. Modelo de trazas en OpenTelemetry

OpenTelemetry reúne especificaciones, APIs, SDKs, convenciones semánticas, librerías de instrumentación y componentes para producir y transportar telemetría.

Dentro de una aplicación, la estructura básica es:

```text
código instrumentado
        |
        v
OpenTelemetry API
        |
        v
OpenTelemetry SDK
        |
        v
exporter
```

La API define las operaciones disponibles para instrumentar código. El SDK implementa la producción, procesamiento y exportación de la señal.

Por ejemplo:

```js
import { trace } from "@opentelemetry/api";

const tracer = trace.getTracer("orders-api");
```

El `Tracer` permite crear spans que representan operaciones.

### 2.1 Trace y span

Una **traza** (`trace`) representa una ejecución lógica formada por operaciones relacionadas.

Un **span** representa una operación con un inicio y un final.

```text
Trace
|
+-- Span
    |
    +-- Span
        |
        +-- Span
```

Un span puede contener:

```text
nombre
trace_id
span_id
parent span
tiempo de inicio
tiempo de finalización
atributos
eventos
estado
tipo de span
```

Ejemplo conceptual:

```text
trace_id = 4d2f...

POST /orders
span_id = a100

    order.create
    span_id = a200

        POST /authorize
        span_id = a300
```

Todos los spans pertenecen a la misma traza porque comparten el mismo `trace_id`.

Cada operación tiene un `span_id` propio.

La relación padre-hijo conserva la estructura de ejecución:

```text
POST /orders
    |
    +-- order.create
            |
            +-- POST /authorize
```

![Anatomía de una traza](images/3.6-anatomia-traza.png)

### 2.2 Duración y relaciones temporales

Cada span registra tiempo de inicio y finalización.

```text
duration = end_time - start_time
```

La duración de un span padre puede incluir la duración de sus hijos.

Por ejemplo:

```text
POST /orders                 357 ms
|
+-- order.create             355 ms
    |
    +-- POST /authorize      352 ms
```

No sería correcto sumar:

```text
357 + 355 + 352
```

como si fueran tres tiempos independientes.

Las operaciones están anidadas. Parte del tiempo de `POST /orders` corresponde al tiempo consumido dentro de `order.create`, y parte del tiempo de `order.create` corresponde a la llamada `POST /authorize`.

### 2.3 Tipos de span

OpenTelemetry utiliza `SpanKind` para describir la relación de una operación con otros componentes.

Para este sistema interesan tres valores:

| `SpanKind` | Uso |
|---|---|
| `SERVER` | recepción de una operación remota |
| `CLIENT` | llamada remota saliente |
| `INTERNAL` | trabajo local dentro del proceso |

La llamada entre servicios puede representarse así:

```text
orders-api                         payment-api

CLIENT POST /authorize  ------->  SERVER POST /authorize
```

Dentro de cada servicio pueden existir operaciones internas:

```text
orders-api
SERVER POST /orders
|
+-- INTERNAL order.create
    |
    +-- CLIENT POST /authorize

payment-api
SERVER POST /authorize
|
+-- INTERNAL payment.authorize
```

La instrumentación automática puede crear los spans HTTP. Los spans que representan conceptos del dominio suelen requerir instrumentación manual.

## 3. Contexto y propagación entre servicios

Las relaciones entre spans requieren conservar información sobre la ejecución activa.

OpenTelemetry utiliza un **Context** para asociar información con la ejecución actual.

Para tracing, la parte central es el **Span Context**, que contiene, entre otros datos:

```text
trace_id
span_id
trace_flags
trace_state
```

Dentro de un proceso, el contexto permite que un nuevo span se relacione con la operación que ya está activa.

```js
await tracer.startActiveSpan("order.create", async (span) => {
  try {
    await authorizePayment();
  } finally {
    span.end();
  }
});
```

Mientras se ejecuta el callback, `order.create` permanece activo.

Si dentro de esa operación se crea otro span, puede quedar asociado como hijo.

```text
order.create
    |
    +-- otra operación
```

En Node.js, el contexto debe mantenerse correctamente a través de operaciones asíncronas como:

```text
Promises
await
callbacks
timers
clientes HTTP
middleware
```

El SDK configura un mecanismo de gestión de contexto para conservar esa relación lógica.

### 3.1 Propagación por HTTP

El contexto en memoria pertenece a un proceso.

Cuando `orders-api` llama a `payment-api`, la relación debe cruzar la red:

```text
orders-api
    |
    | HTTP
    v
payment-api
```

Para ello se serializa información del contexto dentro de la solicitud.

En HTTP, OpenTelemetry utiliza normalmente W3C Trace Context.

El encabezado principal es:

```text
traceparent
```

Su estructura general es:

```text
version-traceid-parentid-flags
```

Ejemplo:

```text
traceparent:
00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

Los campos representan:

```text
versión
trace_id
span_id del contexto propagado
trace flags
```

Supóngase que `orders-api` tiene:

```text
CLIENT POST /authorize
trace_id = T1
span_id  = S3
```

La instrumentación inyecta ese contexto en la solicitud HTTP.

`payment-api` lo extrae y crea:

```text
SERVER POST /authorize
trace_id       = T1
span_id        = S4
remote parent  = S3
```

La red separa los procesos, pero el `trace_id` conserva la pertenencia a la misma traza.

![Propagación de contexto entre servicios](images/3.6-propagacion-contexto.png)

### 3.2 Identificadores con funciones diferentes

El sistema puede utilizar varios identificadores al mismo tiempo.

| Identificador | Función |
|---|---|
| `order_id` | identifica una entidad del dominio |
| `request_id` | correlaciona una solicitud según las reglas de la aplicación |
| `trace_id` | identifica una traza completa |
| `span_id` | identifica una operación dentro de la traza |

Ejemplo:

```text
order_id   = ord-1042
request_id = req-6a73
trace_id   = 4bf92f3577b34da6a3ce929d0e0e4736
```

Una orden puede participar en varias solicitudes.

Una solicitud distribuida puede contener varios spans.

`trace_id` representa el conjunto de operaciones que forman una ejecución.

Una arquitectura de observabilidad puede incorporar `trace_id` y `span_id` en los logs para permitir navegación entre ambas señales.

## 4. Instrumentación de `orders-api` y `payment-api`

La instrumentación se incorporará en etapas. Cada etapa agrega una capacidad y debe comprobarse antes de continuar.

La secuencia es:

```text
1. declarar las dependencias de OpenTelemetry
2. crear y precargar el bootstrap del SDK
3. comprobar spans HTTP y propagación automática
4. agregar spans de dominio
5. enriquecerlos con atributos, eventos y estado
6. identificar cada servicio mediante Resources
7. exportar las trazas hacia Collector y Jaeger
```

El objetivo es distinguir qué evidencia proviene automáticamente de las librerías y qué evidencia debe diseñarse de forma explícita.


La implementación se considera correcta únicamente cuando cada etapa pasa su comprobación:

| Etapa | Cambio realizado | Evidencia que debe aparecer |
|---|---|---|
| bootstrap | SDK + autoinstrumentación | spans HTTP en consola |
| propagación | instrumentación HTTP en ambos procesos | mismo `traceId` en ambos servicios |
| dominio en orders | `order.create` | span manual dentro de `POST /orders` |
| dominio en payment | `payment.authorize` | span manual dentro de `POST /authorize` |
| semántica | atributos, evento y estado | `scenario`, `result`, timeout y `ERROR` cuando corresponde |
| identidad | `OTEL_SERVICE_NAME` | `orders-api` y `payment-api` diferenciados |
| exportación | OTLP + Collector + Jaeger | traza distribuida consultable en Jaeger |

```json
"dependencies": {
```

y agregue las dependencias utilizadas durante esta sesión.

El objeto `dependencies` debe quedar:

#### Comprobar el archivo antes de continuar

Valide que `package.json` siga siendo JSON válido:

```bash
node -e "JSON.parse(require('fs').readFileSync('package.json','utf8')); console.log('package.json válido')"
```

Debe obtener:

```text
package.json válido
```

No ejecute todavía `npm install` en el sistema anfitrión. Los Dockerfiles del repositorio ya contienen:

```dockerfile
COPY package.json ./
RUN npm install --omit=dev
```

Por tanto, cuando se reconstruyan las imágenes, Docker instalará las dependencias declaradas en `package.json`.

El flujo es:

```text
editar package.json
        ↓
docker compose up --build
        ↓
Docker copia package.json
        ↓
npm install --omit=dev dentro de la imagen
        ↓
orders-api y payment-api disponen de OpenTelemetry
```



!!! note "Por qué la instrumentación debe cargarse antes del código de la aplicación"

    Las instrumentaciones de HTTP y Express necesitan instalar sus hooks antes de que esas librerías sean cargadas.

    La secuencia correcta es:

    ```text
    OpenTelemetry
        ↓
    instrumentaciones
        ↓
    Express, HTTP y código de aplicación
    ```

    Inicializar OpenTelemetry después de importar Express puede dejar operaciones fuera de la instrumentación.

### 4.2 Crear el bootstrap de OpenTelemetry

El proyecto utiliza módulos ESM (`"type": "module"` en `package.json`). OpenTelemetry debe inicializarse **antes** de que la aplicación cargue HTTP, Express y las demás librerías que se quieren instrumentar.

Para esta sesión se utilizará un archivo CommonJS pequeño como bootstrap.

Crear:

```text
services/orders-api/src/instrumentation.cjs
```

con el siguiente contenido:

```js
const {
  NodeSDK
} = require("@opentelemetry/sdk-node");

const {
  ConsoleSpanExporter
} = require("@opentelemetry/sdk-trace");

const {
  getNodeAutoInstrumentations
} = require(
  "@opentelemetry/auto-instrumentations-node"
);

function ignoreInfrastructureRequests(req) {
  const path = (req.url ?? "").split("?")[0];

  return (
    path === "/health" ||
    path === "/metrics"
  );
}

const sdk = new NodeSDK({
  traceExporter: new ConsoleSpanExporter(),

  instrumentations: [
    getNodeAutoInstrumentations({
      "@opentelemetry/instrumentation-http": {
        ignoreIncomingRequestHook:
          ignoreInfrastructureRequests
      }
    })
  ]
});

sdk.start();

async function shutdown() {
  try {
    await sdk.shutdown();
  } finally {
    process.exit(0);
  }
}

process.on("SIGTERM", shutdown);
process.on("SIGINT", shutdown);
```

Crear **el mismo archivo** en:

```text
services/payment-api/src/instrumentation.cjs
```

#### Qué hace este archivo

El bootstrap realiza tres tareas.

Primero, crea el SDK:

```js
const sdk = new NodeSDK(...)
```

El SDK coordina la instrumentación y la producción de telemetría dentro del proceso.

Segundo, registra instrumentaciones automáticas:

```js
getNodeAutoInstrumentations(...)
```

Estas instrumentaciones reconocen librerías como HTTP, Express y el cliente HTTP utilizado por `fetch()`.

Tercero, en esta primera etapa utiliza:

```js
new ConsoleSpanExporter()
```

Esto hace que cada span terminado se imprima en la salida estándar del proceso. Todavía no se utiliza Collector ni Jaeger.

La pregunta de esta etapa es:

> ¿Los dos procesos producen spans y conservan el contexto cuando una solicitud cruza de `orders-api` a `payment-api`?

#### Por qué se excluyen `/health` y `/metrics`

Docker consulta `/health` periódicamente para ejecutar sus `healthcheck`.

Prometheus consulta `/metrics` periódicamente para realizar el *scrape*.

Si ambas rutas se instrumentan durante esta demostración, el `ConsoleSpanExporter` genera continuamente spans que no pertenecen a la solicitud que se quiere estudiar.

La función:

```js
ignoreInfrastructureRequests(req)
```

hace que la instrumentación HTTP no trace solicitudes entrantes cuyo path sea:

```text
/health
/metrics
```

Esto **no deshabilita esas rutas**. Docker y Prometheus continúan utilizándolas normalmente. Únicamente se evita producir spans para ellas durante la demostración.

!!! note "Puede aparecer telemetría adicional"

    `getNodeAutoInstrumentations()` habilita varias instrumentaciones. Además de los spans HTTP principales pueden aparecer spans de Express, Router, `undici` o conexiones de red.

    Esos spans son válidos, pero no todos son relevantes para la primera comprobación. En la sección 4.4 se indicará exactamente qué campos localizar.

#### Qué debe existir antes de continuar

Al terminar este paso deben existir:

```text
services/orders-api/src/instrumentation.cjs
services/payment-api/src/instrumentation.cjs
```

Todavía no debe modificarse `orders.js` ni `payments.js`.

### 4.3 Cargar la instrumentación antes de la aplicación

Crear `instrumentation.cjs` no es suficiente. Node debe cargarlo **antes** de `server.js`.

Modificar:

```text
services/orders-api/Dockerfile
```

Localizar el `CMD` actual y reemplazarlo por:

```dockerfile
CMD ["node", "--watch", "--watch-preserve-output", "--experimental-loader=@opentelemetry/instrumentation/hook.mjs", "--require", "./src/instrumentation.cjs", "src/server.js"]
```

Realizar exactamente el mismo cambio en:

```text
services/payment-api/Dockerfile
```

El orden es relevante:

```text
loader hook de OpenTelemetry
        ↓
instrumentation.cjs
        ↓
server.js
        ↓
Express y código de aplicación
```

El loader hook permite que OpenTelemetry intercepte módulos utilizados por una aplicación ESM.

`--require ./src/instrumentation.cjs` ejecuta el bootstrap antes de cargar `server.js`.

#### Reconstruir las imágenes

Como se modificaron `package.json` y los Dockerfiles, reconstruir:

```bash
docker compose down
docker compose up --build -d
```

Durante el build, Docker ejecutará:

```dockerfile
RUN npm install --omit=dev
```

utilizando las dependencias que se agregaron a `package.json`.

Después comprobar:

```bash
docker compose ps
```

Antes de continuar, `orders-api` y `payment-api` deben estar saludables.

#### Si un servicio aparece como `unhealthy`

No reconstruya repetidamente sin identificar primero la causa.

Si falla `payment-api`:

```bash
docker compose logs --tail=100 payment-api
```

Si falla `orders-api`:

```bash
docker compose logs --tail=100 orders-api
```

También puede inspeccionarse el resultado del `healthcheck`:

```bash
docker inspect payment-api \
  --format '{{json .State.Health}}' \
  | jq
```

Un error de sintaxis en `instrumentation.cjs`, un nombre de paquete incorrecto o un problema al precargar OpenTelemetry puede impedir que `server.js` llegue a escuchar en el puerto 3000.

No avanzar a la comprobación de spans hasta que ambos servicios estén saludables.

### 4.4 Comprobar la instrumentación automática

En esta etapa todavía no se han creado spans manuales. La evidencia debe provenir exclusivamente de las instrumentaciones automáticas.

#### Paso 1. Ejecutar una sola solicitud

Ejecutar:

```bash
curl -s \
  -X POST http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{
    "order_id":"ord-auto-001",
    "scenario":"normal"
  }' \
  | jq
```

Debe obtenerse una orden creada.

#### Paso 2. Recuperar únicamente los logs recientes

No utilizar:

```bash
docker compose logs -f ...
```

para esta comprobación.

La opción `-f` sigue la salida indefinidamente y dificulta aislar una sola ejecución.

En su lugar, inmediatamente después del `curl`, guardar los últimos segundos:

```bash
docker compose logs \
  --since=5s \
  orders-api payment-api \
  > /tmp/otel-auto.log
```

Ahora la evidencia queda congelada en un archivo y puede inspeccionarse sin que aparezcan nuevos datos.

#### Paso 3. Reducir la salida a los campos relevantes

Ejecutar:

```bash
grep -nE \
  "traceId:|parentSpanContext:|name: 'POST|url.full:|isRemote:|http.route" \
  /tmp/otel-auto.log
```

El `ConsoleSpanExporter` imprime muchos campos. Para esta comprobación interesan principalmente:

```text
traceId
span id (campo id en la salida del exporter)
parentSpanContext
name
url.full
isRemote
http.route
```

#### Paso 4. Localizar los tres spans principales

Debe poder identificarse conceptualmente:

```text
orders-api
SERVER POST /orders

orders-api
CLIENT POST /authorize

payment-api
SERVER POST /authorize
```

En algunas versiones el span cliente generado por `fetch()` puede aparecer simplemente como:

```text
name: 'POST'
```

En ese caso se reconoce por:

```text
url.full:
http://payment-api:3000/authorize
```

No se debe depender únicamente del nombre del span.

#### Paso 5. Comprobar la propagación

Supóngase que el span cliente de `orders-api` muestra:

```text
traceId: T1
id: S3
url.full: http://payment-api:3000/authorize
```

El span servidor de `payment-api` debe mostrar:

```text
traceId: T1

parentSpanContext:
  traceId: T1
  spanId: S3
  isRemote: true
```

La evidencia demuestra:

```text
orders-api
CLIENT span S3
traceId = T1
        |
        | contexto propagado por HTTP
        v
payment-api
SERVER span S4
traceId = T1
parent = S3
```

El `traceId` se conserva.

El span de `payment-api` tiene un identificador propio.

`isRemote: true` indica que el contexto padre llegó desde otro proceso.

No se agregó manualmente ningún encabezado `traceparent`: la instrumentación automática se encargó de inyectar y extraer el contexto.

#### Qué no debe intentarse interpretar todavía

Pueden aparecer spans como:

```text
middleware - jsonParser
request handler
middleware - patched
tcp.connect
```

Son producidos por otras instrumentaciones automáticas. No son necesarios para establecer la propagación entre ambos servicios.

En esta etapa basta con identificar:

```text
POST /orders
llamada hacia /authorize
POST /authorize
mismo traceId
parent remoto correcto
```

!!! warning "Si aparecen dos `traceId` diferentes"

    Si los spans de `orders-api` y `payment-api` asociados a la misma solicitud tienen `traceId` diferentes, el negocio puede seguir respondiendo correctamente, pero el contexto distribuido no se está propagando.

    Revise primero:

    ```text
    instrumentation.cjs existe en ambos servicios
    ambos Dockerfiles precargan instrumentation.cjs
    el loader hook se ejecuta antes de server.js
    ambos contenedores fueron reconstruidos
    ```

### 4.5 Identificar qué falta en la instrumentación automática

La instrumentación automática conoce HTTP y Express.

Por eso puede representar:

```text
POST /orders
POST /authorize
```

No conoce conceptos propios de esta aplicación como:

```text
crear una orden
autorizar un pago
```

La estructura técnica puede verse aproximadamente así:

```text
SERVER POST /orders
|
+-- CLIENT POST /authorize
        |
        v
    SERVER POST /authorize
```

Se agregarán dos spans manuales:

```text
order.create
payment.authorize
```

para representar esas operaciones de dominio.

### 4.6 Agregar `order.create` en `orders-api`

La autoinstrumentación ya permite observar el límite HTTP, pero todavía no expresa que parte de ese trabajo corresponde a una operación del dominio denominada **crear una orden**.

Para incorporar ese significado se agregará un span manual llamado:

```text
order.create
```

Abrir:

```text
services/orders-api/src/orders.js
```

#### Paso 1. Importar la API necesaria

Al inicio del archivo, junto con las demás importaciones, agregar:

```js
import {
  SpanStatusCode,
  trace
} from "@opentelemetry/api";
```

`trace` permite obtener un `Tracer`.

`SpanStatusCode` se utilizará posteriormente para indicar que una operación terminó con error.

#### Paso 2. Obtener un `Tracer`

Después de las importaciones agregar:

```js
const tracer = trace.getTracer("orders-api");
```

Un `Tracer` es el objeto utilizado por el código de la aplicación para crear spans manuales.

En esta sesión el nombre:

```text
orders-api
```

identifica la instrumentación creada por este código. No sustituye todavía a `service.name`, que se configurará más adelante como atributo de Resource.

#### Paso 3. Hacer que la lógica existente se ejecute dentro de `order.create`

Antes de modificarla, `createOrder()` tiene esta estructura general:

```js
export async function createOrder(req, res) {
  const {
    order_id = "ord-generated",
    scenario = "normal"
  } = req.body;

  // métricas

  try {
    // validación
    // llamada a payment-api
    // creación de la orden
    // respuesta HTTP
  } finally {
    // cierre de métricas
  }
}
```

No se eliminará esa lógica.

Se agregará una capa alrededor de ella:

```js
export async function createOrder(req, res) {
  return tracer.startActiveSpan(
    "order.create",
    async (span) => {

      // aquí permanece la lógica
      // que createOrder() ya tenía

    }
  );
}
```

Por tanto, **envolver la operación** significa mover el cuerpo existente de `createOrder()` dentro del callback recibido por `startActiveSpan()`.

El comienzo de la función debe quedar así:

```js
export async function createOrder(req, res) {
  return tracer.startActiveSpan(
    "order.create",
    async (span) => {
      const {
        order_id = "ord-generated",
        scenario = "normal"
      } = req.body;

      const route = "/orders";

      // el resto de la lógica continúa aquí
```

`startActiveSpan()` realiza dos acciones:

```text
crea el span order.create
        ↓
lo establece como span activo mientras
se ejecuta el callback
```

Esto permite que las operaciones instrumentadas que ocurran dentro del callback conserven la relación de contexto.

Por ejemplo, cuando posteriormente se ejecute:

```js
await authorizePayment(
  order_id,
  scenario
);
```

el span HTTP creado automáticamente para la llamada a `payment-api` podrá quedar como descendiente de `order.create`.

La estructura que se busca es:

```text
SERVER POST /orders
|
+-- order.create
    |
    +-- CLIENT POST /authorize
```

#### Paso 4. Describir la ejecución mediante un atributo

Un span no contiene únicamente tiempos e identificadores. También puede contener **atributos**.

Un atributo es un par:

```text
clave = valor
```

que describe una característica de esa ejecución concreta.

La aplicación permite:

```text
scenario = normal
scenario = slow
scenario = payment-timeout
```

Después de obtener `scenario`:

```js
const {
  order_id = "ord-generated",
  scenario = "normal"
} = req.body;
```

agregar inmediatamente:

```js
span.setAttribute(
  "order.scenario",
  scenario
);
```

El fragmento debe quedar:

```js
const {
  order_id = "ord-generated",
  scenario = "normal"
} = req.body;

span.setAttribute(
  "order.scenario",
  scenario
);

const route = "/orders";
```

Si la solicitud contiene:

```json
{
  "order_id": "ord-1042",
  "scenario": "slow"
}
```

el span incluirá conceptualmente:

```text
order.create
└── attributes
    └── order.scenario = slow
```

El atributo no crea otro span y no altera la lógica de negocio. Únicamente agrega contexto a la evidencia.

En este ejercicio no se agrega `order_id` porque la comparación didáctica se concentra en los tres escenarios. Un identificador de entidad puede ser útil en tracing, pero incorporarlo debe ser una decisión explícita considerando utilidad, privacidad, almacenamiento e indexación en el backend.

#### Paso 5. Registrar el resultado de la operación

También interesa distinguir cómo terminó `order.create`.

Cuando la orden se crea correctamente, antes del `return` HTTP 201 agregar:

```js
span.setAttribute(
  "order.result",
  "created"
);
```

El bloque debe quedar aproximadamente:

```js
const order = {
  order_id,
  status: "created"
};

orders.set(order_id, order);

span.setAttribute(
  "order.result",
  "created"
);

return res.status(201).json(order);
```

Cuando la autorización del pago falla, agregar:

```js
span.setAttribute(
  "order.result",
  "payment_error"
);

span.setStatus({
  code: SpanStatusCode.ERROR
});
```

Esto expresa dos cosas diferentes:

```text
order.result = payment_error
describe el resultado

status = ERROR
indica que la operación representada
por el span terminó con error
```

Para un escenario inválido puede conservarse:

```js
span.setAttribute(
  "order.result",
  "invalid_scenario"
);
```

#### Paso 6. Registrar excepciones inesperadas

Los errores HTTP controlados y las excepciones de JavaScript no son exactamente lo mismo.

Si una operación lanza una excepción inesperada, agregar un `catch`:

```js
catch (error) {
  span.recordException(error);

  span.setStatus({
    code: SpanStatusCode.ERROR
  });

  throw error;
}
```

`recordException(error)` agrega un evento de excepción al span.

Después se vuelve a lanzar el error para conservar el comportamiento de manejo de errores de Express.

#### Paso 7. Cerrar siempre el span

Un span manual debe finalizar explícitamente.

Dentro del `finally` existente, después de cerrar las métricas, agregar:

```js
span.end();
```

El final debe quedar:

```js
finally {
  const statusCode = String(res.statusCode);

  requestsTotal.inc({
    method: req.method,
    route,
    status_code: statusCode
  });

  requestsInProgress.dec({ route });

  endTimer({
    status_code: statusCode
  });

  span.end();
}
```

Utilizar `finally` garantiza que el span se cierre aunque la función termine mediante:

```text
return temprano
respuesta 4xx o 5xx
excepción
```

#### Qué cambió realmente

La lógica funcional continúa siendo la misma.

Se agregaron únicamente elementos de observabilidad:

```text
trace.getTracer(...)
startActiveSpan(...)
setAttribute(...)
setStatus(...)
recordException(...)
span.end()
```

Antes:

```text
POST /orders
    |
    +-- POST /authorize
```

Después:

```text
POST /orders
    |
    +-- order.create
            |
            +-- POST /authorize
```

La instrumentación manual agrega significado del dominio que la instrumentación HTTP no puede inferir por sí sola.

---

??? example "Versión de referencia de `createOrder()` después de instrumentar"

    ```js
    export async function createOrder(req, res) {
      return tracer.startActiveSpan(
        "order.create",
        async (span) => {
          const {
            order_id = "ord-generated",
            scenario = "normal"
          } = req.body;

          const route = "/orders";

          span.setAttribute(
            "order.scenario",
            scenario
          );

          requestsInProgress.inc({ route });

          const endTimer =
            requestDuration.startTimer({
              method: req.method,
              route
            });

          try {
            if (!supportedScenarios.has(scenario)) {
              span.setAttribute(
                "order.result",
                "invalid_scenario"
              );

              return res.status(400).json({
                error: "unknown_scenario",
                supported: [...supportedScenarios]
              });
            }

            const payment =
              await authorizePayment(
                order_id,
                scenario
              );

            if (!payment.ok) {
              span.setAttribute(
                "order.result",
                "payment_error"
              );

              span.setStatus({
                code: SpanStatusCode.ERROR
              });

              if (payment.status === 504) {
                return res.status(504).json({
                  error: "payment_timeout",
                  order_id
                });
              }

              return res.status(502).json({
                error: "payment_error",
                order_id
              });
            }

            const order = {
              order_id,
              status: "created"
            };

            orders.set(order_id, order);

            span.setAttribute(
              "order.result",
              "created"
            );

            return res.status(201).json(order);
          } catch (error) {
            span.recordException(error);

            span.setStatus({
              code: SpanStatusCode.ERROR
            });

            throw error;
          } finally {
            const statusCode =
              String(res.statusCode);

            requestsTotal.inc({
              method: req.method,
              route,
              status_code: statusCode
            });

            requestsInProgress.dec({ route });

            endTimer({
              status_code: statusCode
            });

            span.end();
          }
        }
      );
    }
    ```

    Compare la versión con el archivo original. Debe ser posible señalar qué líneas pertenecen a las métricas Prometheus y cuáles se agregaron exclusivamente para tracing.

```text
payment.authorize
```

#### Paso 6. Representar el timeout

El escenario:

```text

```

es un resultado controlado por la aplicación.

Antes de responder 504 agregar:

```js

  "payment.timeout.detected",
  {
    "payment.timeout_ms":
      scenarioDelay[scenario]
  }
);

  "payment.result",
  "timeout"
);

  code: SpanStatusCode.ERROR
});
```

Aquí se utilizan tres mecanismos con funciones diferentes:

```text
span
payment.authorize
representa la operación y su duración

atributo
payment.result = timeout
describe cómo terminó

evento
payment.timeout.detected
registra un hecho puntual ocurrido
durante la operación
```

El evento contiene además:

```text

```

porque ese valor pertenece al escenario didáctico implementado por `payment-api`.

#### Paso 7. Registrar excepciones inesperadas

Agregar:

```js
catch (error) {

  span.setStatus({
    code: SpanStatusCode.ERROR
  });

  throw error;
}
```

Este bloque se utiliza para excepciones reales de ejecución.

El escenario `payment-timeout` no lanza una excepción: es una respuesta 504 deliberadamente generada por el código. Por eso se registra mediante atributos, evento y estado.

#### Paso 8. Cerrar el span

Agregar:

```js
finally {
  span.end();
}
```

De esta forma el span se termina tanto en el camino exitoso como en los caminos de error.

??? example "Versión de referencia de `authorizePayment()` después de instrumentar"

    ```js
    export async function authorizePayment(req, res) {
      return tracer.startActiveSpan(
        "payment.authorize",
        async (span) => {
          const {
            order_id = "ord-generated",
            scenario = "normal"
          } = req.body;

          span.setAttribute(
            "payment.scenario",
            scenario
          );

          try {
            if (!(scenario in scenarioDelay)) {
              span.setAttribute(
                "payment.result",
                "invalid_scenario"
              );

              return res.status(400).json({

                supported:
                  Object.keys(scenarioDelay)
              });

            await delay(
              scenarioDelay[scenario]

                    scenarioDelay[scenario]
                }
              );

              span.setAttribute(
                "payment.result",
                "timeout"
              );

              span.setStatus({
                code: SpanStatusCode.ERROR
              });

              return res.status(504).json({
                error: "payment_timeout",
                order_id
              });
            }

            span.setAttribute(
              "payment.result",
              "authorized"
            );

            return res.status(200).json({
              order_id,
              status: "authorized"
            });
          } catch (error) {
            span.recordException(error);

            span.setStatus({
              code: SpanStatusCode.ERROR
            });

            throw error;
          } finally {
            span.end();
          }
        }
      );
    }
    ```

## 5. Exportación de trazas: OTLP, Collector y Jaeger

Hasta ahora los spans se imprimen dentro de los contenedores mediante `ConsoleSpanExporter`.

Ese mecanismo permite validar la instrumentación, pero no ofrece almacenamiento ni una interfaz para explorar trazas.

La siguiente arquitectura será:

```text
orders-api -------+
                  |
payment-api ------+---- OTLP ----> Collector ----> Jaeger
```

El procedimiento se realizará en tres pasos:

```text
1. configurar Collector
2. cambiar los SDKs para exportar mediante OTLP
3. agregar Jaeger como backend
```

---

### 5.1 Crear la configuración del Collector

Crear en la raíz del repositorio:

```text
otel-collector-config.yaml
```

con:

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317

      http:
        endpoint: 0.0.0.0:4318

processors:
  batch: {}

exporters:
  debug:
    verbosity: normal

  otlp/jaeger:
    endpoint: jaeger:4317

    tls:
      insecure: true

service:
  pipelines:
    traces:
      receivers:
        - otlp

      processors:
        - batch

      exporters:
        - debug
        - otlp/jaeger
```

La configuración define:

```text
receiver
otlp

processor
batch

exporters
debug
otlp/jaeger
```

El pipeline:

```yaml
traces:
```

conecta esos componentes.

Configurar un receiver o exporter sin incluirlo en un pipeline no hace que procese telemetría.

---

```js
    const {
```

### 5.9 Distinguir tráfico de aplicación y tráfico de telemetría

![Tráfico de aplicación y tráfico de telemetría](images/3.6-trafico-aplicacion-telemetria.png)

El sistema contiene dos flujos diferentes.

#### Tráfico de aplicación

```text
cliente
   ↓
orders-api
   ↓
payment-api
```

Transporta operaciones del sistema:

```text
POST /orders
POST /authorize
```

#### Tráfico de telemetría

```text
orders-api -------+
                  |
payment-api ------+----> Collector ----> Jaeger
```

Transporta spans mediante OTLP.

Una falla en el segundo camino no implica necesariamente que el primero haya fallado.

Puede comprobarse deteniendo únicamente Collector:

```bash
docker compose stop otel-collector
```

Después ejecutar:

```bash
curl -s \
  -o /tmp/no-collector.json \
  -w 'HTTP %{http_code}
' \
  -X POST http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{
    "order_id":"ord-no-collector",
    "scenario":"normal"
  }'

cat /tmp/no-collector.json | jq
```

La solicitud de negocio debe continuar pudiendo terminar con:

```text
HTTP 201
```

aunque el exporter pueda reportar que no logró enviar telemetría.

Reiniciar Collector:

```bash
docker compose start otel-collector
```

Esta prueba separa explícitamente:

```text
disponibilidad del sistema observado
```

de:

```text
disponibilidad del camino de observabilidad
```

## 6. Evidencia producida y límites de interpretación

Los tres escenarios conocidos permiten anticipar qué debería observarse una vez instrumentado el sistema.

### 6.1 Comparación de escenarios

#### `normal`

```text
orders-api
SERVER POST /orders                 ~85 ms
|
+-- order.create                    ~83 ms
    |
    +-- CLIENT POST /authorize      ~80 ms
            |
            v
        payment-api
        SERVER POST /authorize      ~80 ms
        |
        +-- payment.authorize       ~80 ms
```

#### `slow`

```text
orders-api
SERVER POST /orders                ~355 ms
|
+-- order.create                   ~353 ms
    |
    +-- CLIENT POST /authorize     ~350 ms
            |
            v
        payment-api
        SERVER POST /authorize     ~350 ms
        |
        +-- payment.authorize      ~350 ms
```

La topología puede ser igual a la del caso `normal`.

Lo que cambia es la duración.

Una traza lenta no necesita tener una estructura diferente.

#### `payment-timeout`

```text
orders-api
SERVER POST /orders                ~705 ms   ERROR
|
+-- order.create                   ~703 ms   ERROR
    |
    +-- CLIENT POST /authorize     ~700 ms   ERROR
            |
            v
        payment-api
        SERVER POST /authorize     ~700 ms   ERROR
        |
        +-- payment.authorize      ~700 ms   ERROR
```

La evidencia permite localizar el tiempo dentro del camino de `payment-api` y observar que la operación termina con HTTP 504.

El escenario sigue siendo didáctico y determinista. `payment-api` introduce deliberadamente la demora de aproximadamente 700 ms. Esa evidencia no debe interpretarse como prueba de saturación, pérdida de paquetes o una red lenta.

### 6.2 Relación con métricas y logs

Las señales conservan funciones diferentes.

| Pregunta | Señal primaria |
|---|---|
| ¿Cuántas solicitudes por segundo recibe `orders-api`? | métrica |
| ¿Qué proporción termina con 5xx? | métrica |
| ¿Cómo cambia el p95? | métrica |
| ¿Qué eventos quedaron registrados para una solicitud? | log |
| ¿Qué operaciones formaron una ejecución? | traza |
| ¿Dónde se observa el tiempo de una solicitud concreta? | traza |
| ¿Qué ocurrió durante un error específico? | log y traza |

Una investigación puede comenzar en Grafana:

```text
p95 elevado
   |
   v
intervalo problemático
   |
   v
traza lenta
   |
   | trace_id
   +------> logs relacionados
```

La dirección también puede invertirse:

```text
log de error
   |
   | trace_id
   v
traza
```

El valor de la correlación aparece cuando cada señal conserva suficiente contexto para pasar a la siguiente.

### 6.3 Límites de la evidencia

Una traza como:

```text
POST /orders                         356 ms
|
+-- POST /authorize                  352 ms
        |
        +-- payment.authorize        350 ms
```

permite afirmar:

```text
la mayor parte del tiempo observado
se encuentra dentro del camino de autorización
```

No permite establecer por sí sola:

```text
si la CPU estaba saturada
si hubo espera de red
si existió contención
si el proceso estaba bloqueado por I/O
```

Esas hipótesis requieren evidencia adicional.

También debe considerarse **sampling**. En sistemas de alto volumen, no todas las trazas tienen que conservarse.

Por tanto:

> La ausencia de una traza no demuestra necesariamente que la operación no ocurrió.

La interpretación depende de conocer cómo se produjo y retuvo la evidencia.

### 6.4 Criterios para revisar una instrumentación

Antes de considerar adecuada una instrumentación de trazas conviene comprobar:

- OpenTelemetry se inicializa antes de las librerías instrumentadas;
- cada servicio tiene un `service.name` estable;
- los nombres de span describen operaciones y no incluyen valores variables;
- los spans manuales representan trabajo relevante;
- los atributos tienen una función operacional;
- los caminos con `return`, `throw` o timeout terminan correctamente sus spans;
- el estado de cada span corresponde al resultado de la operación que representa;
- el contexto se conserva entre `orders-api` y `payment-api`;
- la exportación de telemetría está separada del código de dominio;
- no se almacenan datos sensibles sin una justificación concreta.

La sesión siguiente partirá de trazas ya producidas y se concentrará en leerlas: reconstruir recorridos, comparar una ejecución normal con una lenta, localizar errores y correlacionar `trace_id` con logs y métricas.
