# 3.7 Trazas distribuidas y correlación de señales

## Propósito

En la sesión anterior se instrumentaron `orders-api` y `payment-api` con OpenTelemetry. Al finalizar ese trabajo, el sistema ya produce trazas con instrumentación automática y manual, propaga contexto entre ambos servicios y exporta la telemetría mediante OpenTelemetry Collector hacia Jaeger.

La pregunta de esta sesión es diferente:

> **¿Cómo utilizar una traza ya producida para reconstruir una solicitud, localizar dónde se observa el tiempo y decidir qué evidencia adicional hace falta?**

El punto de partida es el mismo sistema distribuido:

```text
cliente
   |
   | POST /orders
   v
orders-api
   |
   | POST /authorize
   v
payment-api
```

y los mismos escenarios deterministas:

| Escenario | `payment-api` | Resultado de `orders-api` |
|---|---:|---:|
| `normal` | aproximadamente 80 ms | HTTP 201 |
| `slow` | aproximadamente 350 ms | HTTP 201 |
| `payment-timeout` | aproximadamente 700 ms y HTTP 504 | HTTP 504 |

Los tiempos anteriores describen el comportamiento programado del caso didáctico. Las duraciones observadas en una ejecución concreta pueden incluir overhead adicional de HTTP, runtime, instrumentación y planificación.

Al finalizar la sesión se deberá poder:

1. Reconstruir el recorrido de una solicitud a partir de sus spans y relaciones;
2. Interpretar correctamente la duración de spans anidados y evitar sumas incorrectas;
3. Comparar trazas normales y anómalas para localizar dónde aparece una diferencia;
4. Correlacionar una anomalía agregada con una traza concreta y una traza con logs relacionados;
5. Distinguir evidencia observada, inferencia, hipótesis y conclusión.

## 1. Modelo e interpretación estructural

Una traza distribuida representa una ejecución que atraviesa uno o más componentes. Está formada por **spans**, donde cada span describe una operación observada durante un intervalo.

OpenTelemetry define, entre otros, los siguientes elementos de un span:

```text
nombre
span_id
trace_id
parent span_id
tiempo de inicio
tiempo de finalización
atributos
eventos
estado
```

Un `trace_id` agrupa los spans que pertenecen a la misma ejecución distribuida. Cada span posee además su propio `span_id`.

En el sistema de la clase, una creación de orden puede producir conceptualmente:

```text
orders-api
SERVER POST /orders
|
+-- order.create
    |
    +-- CLIENT POST /authorize
            |
            v
        payment-api
        SERVER POST /authorize
        |
        +-- payment.authorize
```

La representación anterior combina operaciones de distinto tipo:

| Span | Origen | Interpretación |
|---|---|---|
| `SERVER POST /orders` | instrumentación automática | recepción de la solicitud en `orders-api` |
| `order.create` | instrumentación manual | operación de dominio de creación de orden |
| `CLIENT POST /authorize` | instrumentación automática | llamada HTTP saliente desde `orders-api` |
| `SERVER POST /authorize` | instrumentación automática | recepción de la llamada en `payment-api` |
| `payment.authorize` | instrumentación manual | operación de dominio de autorización |

La instrumentación automática describe operaciones que las bibliotecas reconocen. Los spans manuales agregan significado que pertenece al dominio de la aplicación.

### 1.1 Relaciones entre spans

La relación padre-hijo permite reconstruir dependencia causal dentro de una traza.

Considérese:

```text
A  SERVER POST /orders
|
+-- B  order.create
    |
    +-- C  CLIENT POST /authorize
            |
            +-- D  SERVER POST /authorize
                |
                +-- E  payment.authorize
```

En esta representación:

```text
A es padre de B
B es padre de C
C precede causalmente a D a través del límite HTTP
D es padre de E
```

La propagación de contexto permite que el span creado en `payment-api` continúe perteneciendo a la misma traza que comenzó en `orders-api`.

!!! note "Una traza no es únicamente una lista"

    Si solo se dispone de cinco spans sin relaciones, no se conoce todavía la estructura de la ejecución. La información de contexto permite ensamblarlos como una sola traza y establecer sus relaciones.

### 1.2 Reconstrucción de una solicitud

Antes de interpretar duración o errores, debe reconstruirse el recorrido.

Para una traza seleccionada en Jaeger, conviene responder primero:

1. ¿cuál es el span raíz?
2. ¿qué servicio produjo cada span?
3. ¿qué operación ejecuta cada span?
4. ¿qué spans representan límites entre procesos?
5. ¿qué atributos permiten reconocer el escenario ejecutado?

En el caso de estudio, los spans manuales contienen atributos como:

```text
order.scenario
order.result
payment.scenario
payment.result
```

Por ejemplo, una ejecución puede incluir:

```text
order.scenario   = slow
payment.scenario = slow
```

Estos atributos describen la ejecución observada. No crean relaciones entre spans y no sustituyen al contexto de traza.

Con el entorno final de 3.6 levantado:


genere una solicitud normal:

```bash

  -X POST http://localhost:3000/orders \
  -H 'content-type: application/json' \

    "order_id": "ord-trace-normal",
```

Abra:


```text

span_id

```

## 2. Análisis temporal

Una traza permite observar **cuándo comenzó y terminó cada operación**. Esta información es especialmente útil cuando una métrica agregada indica que la latencia aumentó y se quiere conocer dónde aparece el tiempo en ejecuciones concretas.

La duración de un span puede expresarse como:

\[
T_{span}=t_{fin}-t_{inicio}
\]

Sin embargo, la duración de un span debe interpretarse como **tiempo transcurrido observado para esa operación**, no como tiempo de CPU consumido.

Por ejemplo:

```text
payment.authorize    350 ms
```

significa que transcurrieron aproximadamente 350 ms entre el inicio y el final del span.

No significa automáticamente:

```text
350 ms de CPU
350 ms ejecutando instrucciones sin interrupción
350 ms de espera de red
350 ms de I/O
```

Esas afirmaciones requieren evidencia adicional.

### 2.1 Spans anidados y duración

Considérese una traza simplificada:

```text
POST /orders                    357 ms
|
+-- order.create                355 ms
    |
    +-- CLIENT /authorize       352 ms
            |
            +-- SERVER /authorize   350 ms
                |
                +-- payment.authorize 349 ms
```

Una interpretación incorrecta sería sumar:

```text
357 + 355 + 352 + 350 + 349
```

y concluir que la solicitud consumió aproximadamente 1.76 segundos.

Los spans están **anidados**. Gran parte de esos intervalos representa el mismo tiempo observado desde distintas operaciones.

Una forma conceptual de representarlo es:

```text
tiempo ─────────────────────────────────────────────>

POST /orders
[--------------------------------------------------]

order.create
 [-----------------------------------------------]

CLIENT /authorize
    [-------------------------------------------]

SERVER /authorize
      [----------------------------------------]

payment.authorize
       [--------------------------------------]
```

La duración end-to-end continúa siendo aproximadamente la del span raíz:

```text
~357 ms
```

Los spans hijos permiten descomponer dónde se encuentra contenido ese intervalo.

!!! warning "Regla de interpretación"

    **Las duraciones de spans anidados no deben sumarse para obtener la duración total de la solicitud.**

### 2.2 Trabajo exclusivo y trabajo contenido

Considérese:

```text
order.create                    355 ms
└── CLIENT /authorize           352 ms
```

La evidencia permite observar que casi toda la duración de `order.create` contiene la llamada a autorización.

De manera aproximada:

```text
355 ms - 352 ms ≈ 3 ms
```

quedan fuera del intervalo del span hijo.

Eso no debe interpretarse como una medición exacta de CPU del código local. Solo indica que, según los límites de estos spans, la mayor parte del tiempo de `order.create` coincide temporalmente con la llamada de autorización.

### 2.3 Concurrencia y solapamiento

La suma de hijos resulta todavía más problemática cuando existen operaciones concurrentes.

Supóngase:

```text
parent                           500 ms
|
+-- child A                      400 ms
|
+-- child B                      400 ms
```

Si `A` y `B` se ejecutan parcialmente en paralelo:

```text
tiempo ─────────────────────────────────────────────>

parent
[------------------------------------------------]

child A
  [--------------------------------------]

child B
        [--------------------------------------]
```

entonces:

```text
400 ms + 400 ms = 800 ms
```

no representa la duración de `parent`.

La estructura temporal completa importa.

### 2.4 Ruta crítica

La **ruta crítica** es la cadena de trabajo dependiente que determina la duración end-to-end observada.

No debe confundirse con:

```text
el span individual más largo
la suma de todos los spans
el servicio que posee más spans
```

En una traza estrictamente secuencial, identificar la ruta crítica puede ser sencillo. Cuando hay concurrencia, colas, callbacks o múltiples dependencias, debe considerarse el orden y solapamiento temporal.

Jaeger puede visualizar la ruta crítica de una traza. La visualización es útil para orientar la inspección, pero la interpretación debe seguir basándose en las relaciones y tiempos observados.

### 2.5 Comparación `normal` frente a `slow`

Genere primero una ejecución normal y luego una lenta:

```bash
curl -s \
  -X POST http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{
    "order_id": "ord-trace-normal-2",
    "scenario": "normal"
  }'
```

```bash
curl -s \
  -X POST http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{
    "order_id": "ord-trace-slow",
    "scenario": "slow"
  }'
```

La estructura esperada es aproximadamente la misma:

```text
normal

POST /orders                     ~85 ms
└── order.create                 ~83 ms
    └── CLIENT /authorize        ~80 ms
        └── SERVER /authorize    ~80 ms
            └── payment.authorize ~80 ms
```

```text

└── order.create                ~353 ms
    └── CLIENT /authorize       ~350 ms
        └── SERVER /authorize   ~350 ms

```

La diferencia relevante no es necesariamente la topología.

La evidencia sugiere:

```text
misma operación distribuida
        +
diferencia temporal localizada
en el camino de autorización
```

!!! question "Conclusión sustentada"

    ¿Cuál de las siguientes afirmaciones está mejor sustentada por la comparación?

## 3. Errores y ejecuciones anómalas

Una traza no solo contiene tiempos. Los spans pueden incluir atributos, eventos y estado que permiten describir cómo terminó una operación.

En 3.6, `payment.authorize` se instrumentó para que el escenario `payment-timeout` produzca evidencia como:

```text
payment.scenario = payment-timeout
payment.result   = timeout
```

además de un evento:

```text
payment.timeout.detected
```

con:

```text
payment.timeout_ms = 700
```

y estado de error para la operación correspondiente.

### 3.1 Generar el escenario `payment-timeout`

Ejecute:

```bash
curl -s \
  -o /dev/null \
  -w 'HTTP %{http_code}\n' \
  -X POST http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{
    "order_id": "ord-trace-timeout",
    "scenario": "payment-timeout"
  }'
```

El resultado esperado de `orders-api` es:

```text
HTTP 504
```

Localice la traza en Jaeger.

La estructura esperada es aproximadamente:

```text
POST /orders                    ~705 ms   ERROR
└── order.create                ~703 ms   ERROR
    └── CLIENT /authorize       ~700 ms   ERROR
        └── SERVER /authorize   ~700 ms   ERROR
            └── payment.authorize ~700 ms ERROR
```

Las duraciones exactas pueden variar.

### 3.2 Estado, atributos y eventos

Estos mecanismos tienen funciones diferentes.

| Mecanismo | Pregunta que ayuda a responder |
|---|---|
| nombre del span | ¿qué operación representa? |
| duración | ¿cuánto tiempo transcurrió dentro de sus límites? |
| atributo | ¿qué característica tuvo esta ejecución? |
| evento | ¿qué hecho puntual ocurrió durante el span? |
| estado | ¿cómo terminó la operación desde la perspectiva del span? |

Para `payment.authorize`:

```text
span
payment.authorize

atributos
payment.scenario = payment-timeout
payment.result   = timeout

evento
payment.timeout.detected
payment.timeout_ms = 700

estado
ERROR
```

No es necesario duplicar toda la información en todos los mecanismos.

### 3.3 Error observado y mecanismo de falla

A partir de la traza puede afirmarse que:

```text
la solicitud terminó con 504

la autorización de pago aparece en el camino
de la solicitud afectada

la operación payment.authorize fue observada
durante aproximadamente 700 ms

la instrumentación registró el evento
payment.timeout.detected
```

En este caso particular existe además conocimiento del código didáctico: `payment-api` introduce deliberadamente una demora de aproximadamente 700 ms antes de producir el 504.

Debe distinguirse entre:

```text
evidencia de la traza
```

y:

```text
conocimiento del mecanismo programado
en el caso de estudio
```

En un sistema real, una traza que muestra un span de 700 ms no permite deducir automáticamente cuál mecanismo interno produjo esa duración.

!!! question "Clasificación de afirmaciones"

    Para la traza `payment-timeout`, clasifique cada afirmación como **observación**, **hipótesis** o **conclusión sustentada con información adicional del caso didáctico**:

    1. `payment.authorize` duró aproximadamente 700 ms.
    2. La red perdió paquetes durante la solicitud.
    3. El escenario programado introduce una demora de 700 ms.
    4. `orders-api` recibió un 504 desde el camino de autorización.
    5. `payment-api` estuvo saturado de CPU.

Una clasificación razonable es:

| Afirmación | Clasificación |
|---|---|
| 1 | observación de la traza |
| 2 | hipótesis no sustentada |
| 3 | conclusión sustentada por el código del caso didáctico |
| 4 | observación de la ejecución |
| 5 | hipótesis no sustentada |

## 4. Correlación de señales

Una sola señal rara vez responde todas las preguntas de una investigación.

En este curso se han utilizado tres tipos principales de evidencia:

| Señal | Fortalezas |
|---|---|
| métricas | comportamiento agregado, tendencias, tasas, distribuciones |
| logs | eventos y contexto registrado por la aplicación |
| trazas | estructura y tiempos de ejecuciones concretas |

La correlación consiste en poder pasar de una señal a otra manteniendo suficiente contexto.

### 4.1 Métricas y trazas

Una métrica puede indicar:

```text
el p95 de POST /orders aumentó
```

pero no identifica necesariamente cuál solicitud produjo la observación extrema ni qué operaciones participaron en ella.

Una secuencia de investigación razonable es:

```text
métrica
   |
   v
intervalo anómalo
   |
   v
trazas del mismo intervalo
   |
   v
solicitudes concretas
   |
   v
operaciones donde aparece el tiempo
```

La dirección no implica causalidad. Solo reduce progresivamente el espacio de búsqueda.

Por ejemplo:

```text
Grafana
p95 de /orders elevado
        |
        v
Jaeger
trazas de orders-api en ese intervalo
        |
        v
traza lenta
        |
        v
payment.authorize concentra
gran parte del tiempo observado
```

La nueva evidencia permite formular una pregunta más específica:

> ¿Por qué `payment.authorize` estuvo activo durante ese intervalo?

Esa pregunta podría requerir métricas de recursos, logs, red, I/O o profiling.

### Actividad 2. Correlación temporal

Genere varias solicitudes normales y una lenta:

```bash
for i in 1 2 3 4 5; do
  curl -s \
    -X POST http://localhost:3000/orders \
    -H 'content-type: application/json' \
    -d "{
      \"order_id\": \"ord-normal-$i\",
      \"scenario\": \"normal\"
    }" > /dev/null
done

curl -s \
  -X POST http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{
    "order_id": "ord-slow-correlation",
    "scenario": "slow"
  }' > /dev/null
```

Observe el intervalo correspondiente en Grafana o Prometheus y luego inspeccione en Jaeger las trazas recientes de `orders-api`.

La pregunta no es simplemente:

> ¿Existe una traza lenta?

La pregunta es:

> ¿La evidencia de una ejecución concreta es compatible con el cambio observado en la señal agregada?

### 4.2 El problema de correlacionar con logs

Supóngase que Jaeger muestra una traza problemática con:

```text
trace_id = 4f...c2
```

Ahora se quiere responder:

> ¿Qué eventos de aplicación se registraron durante esta misma ejecución distribuida?

Si los logs no contienen el `trace_id`, buscar por ese identificador no es posible.

Esta situación revela una limitación del diseño de telemetría:

```text
traza disponible
      |
      v
trace_id conocido
      |
      v
logs sin trace_id
      |
      v
correlación incompleta
```

La solución no consiste en copiar todos los datos de la traza dentro de cada log.

Basta con conservar un identificador común.

El modelo de datos de logs de OpenTelemetry contempla explícitamente:

```text
TraceId
SpanId
```

para correlacionar un registro con el contexto de ejecución que estaba activo cuando se emitió.

### 4.3 Modificación guiada: agregar contexto de traza a logs JSON

Para mantener el foco de esta sesión, no se construirá un nuevo pipeline de logging. Se emitirá JSON estructurado a `stdout` y se reutilizarán los principios estudiados en logging estructurado.

Crear en ambos servicios un archivo:

```text
src/trace-log.js
```

En:

```text
services/orders-api/src/trace-log.js
services/payment-api/src/trace-log.js
```

usar:

```js
import {
  context,
  isSpanContextValid,
  trace
} from "@opentelemetry/api";

export function logEvent(
  level,
  event,
  fields,
  msg
) {
  const activeSpan = trace.getSpan(
    context.active()
  );

  const spanContext =
    activeSpan?.spanContext();

  const traceFields =
    spanContext &&
    isSpanContextValid(spanContext)
      ? {
          trace_id: spanContext.traceId,
          span_id: spanContext.spanId
        }
      : {};

  const record = {
    timestamp: new Date().toISOString(),
    level,
    event,
    ...traceFields,
    ...fields,
    msg
  };

  console.log(
    JSON.stringify(record)
  );
}
```

La función obtiene el span asociado con el contexto activo.

Si existe un contexto válido, el registro incorpora:

```text
trace_id
span_id
```

como campos JSON de primer nivel.

Esto sigue una convención interoperable para formatos de log que no utilizan OTLP directamente.

!!! note "Qué significa cada identificador"

    En un log de esta actividad:

    ```text
    trace_id
    ```

    permite relacionar eventos que pertenecen a la misma ejecución distribuida.

    ```text
    span_id
    ```

    identifica la operación activa desde la que se emitió ese log.

    ```text
    order_id
    ```

    identifica una entidad del dominio.

    Son identificadores con funciones diferentes.

### 4.6 Reconstruir una ejecución desde los logs

Reconstruya las imágenes:

```bash
docker compose up --build -d
```

Genere:

```bash
curl -s \
  -o /dev/null \
  -w 'HTTP %{http_code}\n' \
  -X POST http://localhost:3000/orders \
  -H 'content-type: application/json' \
  -d '{
    "order_id": "ord-log-correlation",
    "scenario": "payment-timeout"
  }'
```

Abra la traza correspondiente en Jaeger y copie el `trace_id` completo.

Defínalo en la shell:

```bash
TRACE_ID='<trace_id-completo>'
```

Luego consulte los logs de ambos servicios:

```bash
docker compose logs \
  --no-color \
  --no-log-prefix \
  orders-api payment-api \
| jq -R \
  --arg trace_id "$TRACE_ID" \
  'fromjson?
   | select(.trace_id == $trace_id)'
```

El resultado debería contener eventos procedentes de ambos servicios con el mismo `trace_id`.

Conceptualmente:

```json
{
  "event": "order.creation_started",
  "trace_id": "...",
  "span_id": "...",
  "order_id": "ord-log-correlation"
}
```

```json
{
  "event": "payment.authorization_started",
  "trace_id": "...",
  "span_id": "...",
  "order_id": "ord-log-correlation"
}
```

```json
{
  "event": "payment.authorization_timeout",
  "trace_id": "...",
  "span_id": "...",
  "order_id": "ord-log-correlation"
}
```

Los tres registros pueden compartir `trace_id` pero presentar distintos `span_id`.

Eso es esperado.

La correlación obtenida es:

```text
Jaeger
trace_id
   |
   v
logs de orders-api
   +
logs de payment-api
   |
   v
eventos de la misma ejecución
```

### 4.7 Qué aporta la correlación

La traza puede mostrar:

```text
payment.authorize    ~700 ms
```

El log puede agregar:

```text
event = payment.authorization_timeout
timeout_ms = 700
order_id = ord-log-correlation
```

No se trata de escoger entre log o traza.

Cada señal responde una parte diferente de la investigación:

```text
traza
¿qué operaciones participaron?
¿cómo se relacionaron?
¿dónde aparece el tiempo?

log
¿qué evento decidió registrar la aplicación?
¿con qué contexto de dominio?
¿qué condición fue detectada?
```

La correlación permite usar ambas evidencias sobre la misma ejecución.

## 5. Alcance de la evidencia

El valor de una traza depende tanto de lo que permite observar como de reconocer lo que no demuestra.

Considérese:

```text
POST /orders                    706 ms
└── order.create                704 ms
    └── CLIENT /authorize       701 ms
        └── SERVER /authorize   700 ms
            └── payment.authorize 700 ms
```

Esta evidencia sustenta una afirmación como:

> La mayor parte del tiempo observado para esta solicitud se encuentra dentro del camino de autorización de pago.

No sustenta por sí sola:

> `payment-api` estuvo ejecutando en CPU durante 700 ms.

Tampoco sustenta:

> La red fue responsable de la latencia.

Ni:

> Existió contención por memoria.

Ni:

> El proceso estuvo bloqueado por I/O.

Una secuencia de razonamiento adecuada es:

```text
observación
payment.authorize ≈ 700 ms
        |
        v
interpretación
el tiempo aparece dentro del
camino de autorización
        |
        v
hipótesis
CPU / red / I/O / dependencia /
cola / bloqueo / otra causa
        |
        v
evidencia adicional
        |
        v
diagnóstico
```

### 5.1 Qué evidencia solicitar después

La siguiente fuente depende de la hipótesis.

| Hipótesis | Evidencia adicional posible |
|---|---|
| CPU saturada | utilización, throttling, profiling |
| espera de red | latencia de red, retransmisiones, sockets |
| I/O bloqueante | estados de procesos, syscalls, tiempos de I/O |
| saturación de una dependencia | métricas y trazas de la dependencia |
| cola interna | profundidad de cola, tiempos de espera, instrumentación adicional |
| error de aplicación | logs, eventos, excepciones, atributos |

La elección de una herramienta debe venir después de formular la pregunta.

### 5.2 Correlación no implica causalidad

Si durante el mismo intervalo se observan:

```text
p95 ↑
CPU ↑
```

la coexistencia temporal permite formular una hipótesis.

No demuestra:

```text
CPU ↑  causó  p95 ↑
```

De manera similar:

```text
span lento
+
log de timeout
```

pueden describir el mismo incidente sin demostrar por sí solos todos los mecanismos internos que lo produjeron.

### 5.3 Muestreo y evidencia ausente

En sistemas de producción puede aplicarse sampling para limitar costo y volumen.

Por tanto:

> La ausencia de una traza no demuestra necesariamente que la solicitud no ocurrió.

Para interpretar correctamente la evidencia debe conocerse:

```text
qué se instrumentó
qué se muestreó
qué se exportó
qué se retuvo
```

En el entorno didáctico de esta sesión se trabaja con un volumen pequeño y controlado, por lo que se espera poder localizar las solicitudes generadas durante la actividad.

### 5.4 Ejercicio integrador

Considérese la siguiente evidencia obtenida durante un intervalo en el que Grafana mostró un aumento del p95 de `POST /orders`.

#### Traza A

```text
POST /orders                      92 ms
└── order.create                  90 ms
    └── CLIENT /authorize         85 ms
        └── SERVER /authorize     83 ms
            └── payment.authorize 80 ms
```

#### Traza B

```text
POST /orders                     368 ms
└── order.create                 365 ms
    └── CLIENT /authorize        361 ms
        └── SERVER /authorize    358 ms
            └── payment.authorize 355 ms
```

#### Logs correlacionados con la traza B

```json
{
  "level": "info",
  "event": "order.creation_started",
  "trace_id": "trace-b",
  "span_id": "span-order",
  "order_id": "ord-3107",
  "scenario": "slow"
}
```

```json
{
  "level": "info",
  "event": "payment.authorization_started",
  "trace_id": "trace-b",
  "span_id": "span-payment",
  "order_id": "ord-3107",
  "scenario": "slow"
}
```

```json
{
  "level": "info",
  "event": "payment.authorized",
  "trace_id": "trace-b",
  "span_id": "span-payment",
  "order_id": "ord-3107",
  "scenario": "slow"
}
```

Responda:

1. ¿Qué diferencia estructural existe entre las trazas A y B?
2. ¿Dónde aparece la mayor diferencia temporal?
3. ¿Puede concluirse que `payment-api` consumió CPU durante 355 ms?
4. ¿Qué relación existe entre los tres logs mostrados?
5. ¿Qué aporta `order_id` que no aporta `trace_id`?
6. ¿Qué evidencia adicional sería necesaria para sostener una hipótesis de saturación de CPU?
7. Si la hipótesis fuera espera de red, ¿qué evidencia tendría que consultarse?
8. ¿Qué afirmación puede hacerse con suficiente respaldo utilizando solamente la evidencia mostrada?

Una respuesta adecuada para la última pregunta sería:

> La traza B presenta una latencia mayor que la traza A y la mayor diferencia temporal aparece dentro del camino de autorización de pago. Los logs muestran eventos de la misma ejecución distribuida y permiten relacionarla con la orden `ord-3107`. La evidencia disponible no identifica todavía el mecanismo que produjo la mayor duración.

### Síntesis

El proceso trabajado en esta sesión puede representarse como:

```text
pregunta operacional
        |
        v
métrica
detecta comportamiento agregado
        |
        v
traza
localiza una ejecución y sus operaciones
        |
        v
logs
aportan eventos y contexto
        |
        v
interpretación
        |
        v
hipótesis
        |
        v
evidencia adicional
        |
        v
decisión o diagnóstico
```

La traza es una fuente de evidencia especialmente útil para responder **dónde** aparece el tiempo dentro de una ejecución distribuida.

La explicación de **por qué** aparece ese tiempo puede requerir observar mecanismos que la traza no representa.
